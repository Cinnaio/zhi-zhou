## 零、结论先行

**你的方向可行，而且今天执行就能做到可见性零变化**——四条关键断言全部实测成立（第二节）。

但有**一处必须先修的耦合**：正则目前还兼着一个不相干职责——**过滤分类名**。实测有
**6 个分类名**（`sm`、`双处`、`强取豪夺`、`纯肉`、`肉文`、`调教`）在安全模式下是靠正则
从分类栏隐藏的。若直接删掉正则、让 `isRestrictedContent` 只认字段，这 6 个分类会
**漏出**到安全模式的分类栏。这是整个方案里**唯一会静默回归的点**。

tag 与 LLM 两条路：**tag 优先做**（能再收 128 本，`unknown` 降到约 68）；
**LLM 建议立项**，但前置是新增判定来源字段，否则机器判定会与人工判定混在一起无法追溯。

## 一、先厘清：现在是「两套依据」吗

`ContentPolicyContext.tsx:130`：

```ts
isAllowed = (adultContentEnabled && mode === 'adult') || !isRestrictedContent(metadata)
//            └─ A：读者侧全局开关 ─┘              └─ B：作品侧判级 ─┘
```

这两者不是"两个分级标准"，而是**闸门与标的**：

- **A（读者开关）**：`app_settings.adult_content_enabled` + 读者 `contentMode`（safe/adult）
  决定"这个人愿不愿意看限制级"。**必须保留**——它是 18 岁合规确认的唯一载体。
- **B（作品判级）**：`novels.content_rating` 字段 + 正则兜底。决定"这本书算不算限制级"。

**你要统一的是 B 内部的两条依据**（字段 vs 正则），这是对的。A 不能并入 B，
否则会丢掉"读者自主选择 + 18 岁确认"这层语义（那不是分级，是授权）。

> 另有第三套易混淆的概念：`AiWritingPanel` 的 `adultContentMode: 'off' | 'explicit'`
> （`writing-preferences.ts`）是**创作侧参数**，控制 AI 写不写露骨内容，与读者可见性无关。
> 建议不合并，但文案上统一术语。

## 二、四条实测断言（决定方案可行性）

| # | 断言 | 实测结果 | 含义 |
|---|---|---|---|
| 1 | 命中正则的书是否都已是 `restricted` | **0 本偏差** | 字段与正则**当前完全一致**，无冲突 |
| 2 | 196 本 `unknown` 里正则能兜住几本 | **0 本** | 去掉正则回落，**今日可见性零变化** |
| 3 | 正则是否还兼着分类名过滤 | **6 个分类**靠它隐藏 | **唯一回归风险** |
| 4 | `unknown` 里带成人标签的本数 | **128 / 196** | tag 兜底后仍需人工的仅 **68 本** |

**断言 1+2 是方案成立的前提**：字段与正则结果完全重合，且 `unknown` 全都不是正则命中项，
所以「删掉作品级正则回落、只读字段」在**今天不会改变任何一本书的可见性**。

**断言 3 是必须先补的洞**。`Home.tsx:176` 与 `:219` 把**分类名本身**（纯字符串）送进
`isRestrictedContent`：

```ts
const visibleCategories = safeMode
  ? availableCategories.filter((category) => !isRestrictedContent(category))
  : availableCategories
```

若 `isRestrictedContent` 不再处理字符串，这 6 个分类会显示在安全模式的分类栏。
**必须给分类名单独一条规则，不能简单删掉字符串分支。**

## 三、方案 A（推荐）：统一到字段 + 分类黑名单

### 3.1 设计

保留一个判级入口，但**明确区分两种输入**：

```ts
// 作品判级：只读字段，不再猜文本
function isRestrictedNovel(novel): boolean {
  return novel.contentRating === 'restricted'
}

// 分类名过滤：独立的显式黑名单（不再复用作品判级逻辑）
const RESTRICTED_CATEGORIES = new Set(['sm', '双处', '强取豪夺', '纯肉', '肉文', '调教'])
function isRestrictedCategory(name: string): boolean {
  return RESTRICTED_CATEGORIES.has(name)   // 精确匹配，不用子串
}
```

### 3.2 为什么分类名用「精确枚举」而不是正则

- 分类名是**封闭集合**（本库仅 43 个），精确枚举比正则更准、更可审计
- 正则匹配分类名会误伤相邻项（`/肉/` 之类会连带影响其他分类）
- 枚举表可加注释写明来源，改动可 review

### 3.3 `unknown` 怎么办（统一后的关键取舍）

| 选项 | 含义 | 后果 |
|---|---|---|
| X1：`unknown` 视为受限 | 严格 | 196 本 `unknown` 全部从安全模式消失（含 68 本无成人标签的）→ **不可接受** |
| X2：`unknown` 视为放行 | 宽松 | 196 本全部对安全模式可见（含 128 本带成人标签的）→ **不可接受** |
| **X3：先用 tag/LLM 把 `unknown` 收干净，再统一（推荐）** | 渐进 | 切换时无争议 |

**推荐 X3**：不要在 `unknown` 清空之前切换判定。这意味着**正确顺序是
「先补 tag 判定 → 再统一依据」，而不是反过来**。

## 四、tag 判定：能做，收益明确

### 4.1 数据

`unknown` 196 本中 **128 本带成人标签**（`h` 74、`兄妹` 38、`np` 34、`强制` 7，含交叉）。
tag 判定后仍需人工的仅 **68 本**。

### 4.2 为什么 `h` / `np` 无歧义

现有正则漏掉它们的原因很具体：`/高\s*h|h\s*高/` 要求与「高」连用，`/h\s*文/` 要求构成
「h文」——**单独的标签 `h` 不匹配任何一条**；`np` 则完全没有规则。

跨站验证：`czbooks.net` 虽在代码中是预设名「小說狂人」（`presets.ts:46`，字面为综合站），
但其上 17 本实测**实际内容均为成人向**（`花间淫事`「变态纯肉高H…粗口道具强奸监禁」、
`软妹挨操记`「为满足性幻想…只为方便吃肉」）。**故 `h` 语义跨站一致，白名单可通用。**

### 4.3 但有歧义的标签要分层

`兄妹` 在本库基本都伴随成人情节，但它**同时是题材标签**（骨科文），
用它会把「清水骨科」也拦掉。`强制` / `囚禁` / `暗黑` 同理。

| 层 | 标签 | 处理 |
|---|---|---|
| 高置信 | `h`、`np`、`肉`、`肉文`、`纯肉` | 直接判 `restricted` |
| 中置信 | `兄妹`、`强制`、`囚禁`、`双处`、`调教` | 判 `restricted` + 列入人工抽检 |
| 低置信 | `暗黑`、`虐`、`粗口` | 不判级 |

### 4.4 两条红线

1. **仍然只写 `restricted`，绝不写 `general`**——标签也是枚举法，理由同预填。
2. **必须精确匹配分类数组元素**，不可对拼接文本做子串匹配。`h` 若子串匹配会命中
   任何含 h 的词（英文名、拼音）。**这是实现时最容易写错的地方。**

## 五、LLM 判定：值得做，但先定一件事

### 5.1 它能解决什么

- 收掉 tag 之外的 **68 本**（无成人标签的）
- **未来新书自动初判**——这是唯一能真正"自动化"的路径

### 5.2 成本与风险

| 项 | 评估 |
|---|---|
| 成本 | 398 本一次性输入量很小（标题+简介+分类，约 200 字/本）；项目已有 AI 文本通道（`AI_TEXT_*`） |
| 稳定性 | 同一本书两次调用可能给不同结果 → 需记录判定理由与模型版本 |
| **可审计性** | **核心问题**：模型判的与人判的混在同一字段，事后无法区分 |
| 合规 | 判定涉及成人内容，需确认所用模型允许此类输入 |

### 5.3 必须先定的一件事

**模型判定是否等同于人工判定？** 我建议**否**，应新增判定来源字段：

```sql
ADD COLUMN content_rating_source TEXT NOT NULL DEFAULT 'none'
-- 'none' | 'prefill' | 'tag' | 'llm' | 'human'
```

没有来源标记，就无法回答"这 398 本里哪些是已复核的、哪些是机器猜的"，
也无法实现"人工判定优先、机器不覆盖人工"的既有原则。**这是 LLM 方案的前置条件。**

### 5.4 与 tag 的关系

不是二选一：**tag 做第一道**（便宜、确定、可解释），**LLM 做剩下 68 本 + 新书**。
LLM 结果建议**先进待审队列**而非直接落 `restricted`，人工一键确认。

## 六、回答「还是不做任何修改」

**我建议做，但顺序很重要**，分四次独立落地，每次可单独验收：

1. **补分类名黑名单**（断言 3 的 6 个分类）→ 消除切换前唯一回归风险
2. **补 tag 判定**（`h`/`np` 等高置信）→ `unknown` 196 → ~68
3. **统一依据**（作品级只读字段，移除正则回落）→ 此时可见性零变化
4. LLM 单独立项，前置是新增来源字段

**若只做第 3 步而不做 1、2**：安全模式会漏出 6 个分类名，且 196 本 `unknown` 的归置
变成非此即彼的二选一（X1/X2 都不可接受）。

**若什么都不做**：当前状态是"能跑但不统一"——字段已生效、正则仍兜底、两套依据结果
恰好一致（断言 1）。**这个状态是安全的**，只是不干净。急不急由你定。
